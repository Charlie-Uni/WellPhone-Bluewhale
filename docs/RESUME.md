# 交还后的安全恢复

本轮范围：同一进程中，继续原来授权的一轮任务。用户交还全部相关会话后自动进入只读核对；不重新生成计划、不扩大邮箱范围、不重置步数预算。进程退出或 shell 断连后不自动恢复，需要重新授权。

## 接管和交还

接管先增加 E；有运行任务时停在 DRAINING，取消并等待旧执行结束，把当前事项的写入状态落盘，再读取人工操作前的日历页面，最后开放 HUMAN。整段触摸和文字动作也必须结算。隐藏小窗保持 HUMAN；交还不是隐藏。

交还先撤销文字草稿、清理触摸并等待文字回执，再增加 E。两个会话都回到 AGENT 后，新执行器首先观察 A/B，不启动 App、不发 ACTION_INSERT、不使用旧节点或 Save 票据。缓存的本轮邮件、已完成事项和当前阶段继续使用；旧确认卡和晚到响应失效。

## 分支规则

| 当前页面 / 状态 | 行为 |
| --- | --- |
| 查重或冲突检查时暂停，当前没有内容编辑页 | 重新走读取与冲突检查，保持原授权 |
| 当前事项的编辑页；支持的标题/备注/日期/时间/提醒/截止变化 | 对照人工操作前页面，核对其他节点未变和来源标记；保留新设置，校验提醒先于截止；事件重查冲突，新确认后只点击 Save，再离开、搜索、重开核实 |
| 用户已保存，当前是能核对的事项详情 | 沿用能读回的修改，重新搜索并打开核实，用新时间重查冲突，不再保存 |
| Save 已发出或回执未知 | 只查询和核实；不重新授权同一次 Save。若仍是编辑页，请用户先处理 |
| 模糊或无效时间、账号/日历/时区变化、来源标记删除、未知节点/窗口变化、控件树截断 | 保留当前页面和检查点，提示人工处理；不填旧值、不关闭草稿、不继续导航到下一事项 |
| 邮箱仍有未保存的内容，且本轮还需要读邮箱 | 停在恢复提示；邮件已缓存时后续只处理日历，不操作邮箱草稿 |

支持的字段 resourceId 是有限兼容配置，尚未真机验证。账号、日历/列表必须可明确定位；事件按 start_date/start_time、end_date/end_time（含 event_ 别名）读取。任务的通知使用 task_/reminder_/notification_ 日期与时间；deadline_/task_deadline_/due_ 专用于截止，不再作为通知的别名。日期必须含年，时间支持 24 小时或明确 AM/PM，按配置 IANA 时区转 UTC。重复角色、文本/描述矛盾、夏令时缺口/重叠和无效区间均停止。只有完整、无歧义的值才可核实，不从未知日期选择器猜测。

事件从唯一 notification/event_reminder/reminder_offset/reminder_minutes 控件读取当前提前量，支持分钟、小时和天，中文或英文，范围 1 分钟至 365 天。改变开始时间时沿用当前提前量，改变提前量时采用新设置。关闭提醒、零分钟、多条提醒、未知自定义形式均保留页面。通知字符串出现在其他位置不能替代该角色；保存、重开和重跑都核对此角色。

任务分别读取通知与截止设置：

- 有明确的原生截止日期/时间角色时，以这些控件为准；两者缺一或出现重复角色就停止，不借用备注补齐。用户只改日期时，沿用仍能明确读取的时刻。
- 没有原生截止控件时，只从唯一备注字段中的单条“截止：”行读取，支持完整 ISO 本地日期时间或带偏移日期时间。带偏移时必须符合配置时区的实际偏移；仅写日期不默认补 23:59。多行截止、删掉原有截止、格式不明或夏令时歧义均停止。
- 原生截止与备注同时存在时，原生控件为当前设置，备注按用户内容原样保留；确认卡单独显示“截止设置”，核实不能用备注掩盖原生控件中的旧值。没有这类控件的 Google Calendar/Tasks 路径，截止仍保存在上述结构化备注行中，不声称创建了原生任务截止字段。

通知必须严格早于新截止，相等也阻止恢复；事件提醒还必须早于开始。失败提示用户调整提醒或截止，保持当前页面、HUMAN_HELD 和游标；不保存、不导航到下一事项、不自动改为旧值。提醒和截止可以分别修改，也可一起修改。任务提醒不占用日历忙碌区间；事件继续按新起止时间复查冲突。

编辑页仅放行当前目标类型的支持字段值；节点身份、布局和其余字段保持封印。界面重排可能保守阻止恢复。搜索框属于导航。恢复没有新增权限、直接写入接口或自动改写备注。

## 新时间的冲突复查

未保存表单不能为了查看日程而被导航离开。恢复分支使用 Android CalendarContract 的只读本机查询，未添加 WRITE_CALENDAR；普通流程仍 GUI 检查和保存。工作台新增主动的 READ_CALENDAR 授权入口，后台不会弹系统授权或切到主屏。依据见 [Android Calendar Provider](https://developer.android.com/identity/providers/calendar-provider) 和 [Instances](https://developer.android.com/reference/android/provider/CalendarContract.Instances)。

先在配置账号的可见日历中唯一匹配目标日历，要求可读且启用同步，然后查询该账号全部可见日历的 Instances，覆盖新起止区间、跨日、全天和重复事件实例。半开区间比较；取消和空闲事件不阻塞，精确来源标记排除自身，重复来源标记降为范围未知。数据仅用于本机确认，不发模型。覆盖声明仅为本机已同步数据；其他账号、隐藏日历和未同步云端变更不包括在内。

缺权限、找不到目标、未同步/不可读范围、异常或超大范围，都返回“检查范围不完整”，不会报无冲突。确认卡展示新起止时间、提醒、冲突区间及覆盖边界；用户可接受冲突/边界继续，或保留页面接管处理。恢复阶段保持当前表单，只提供这两个选项；要标待改约或转提醒，先接管调整。普通创建流程的三个冲突选项继续保留。

新确认绑定 E 和当前内容，原来的冲突选择失效。确认后再次只读查询，忙碌区间或覆盖状态变化就停住，保持 HUMAN_HELD，要求重新交还并确认。Save 票据额外绑定整张页面快照，页面再变也会停止。这是两次快照检查，并非日历跨应用事务，第二次检查到保存之间仍有竞态。恢复查询不创建、丢弃或保存其他事项。

## 状态和持久化

WorkflowCheckpoint 在内存保留授权范围、已读取邮件、已完成结果与当前事项阶段，不保留模型动作或 Save 票据。内容不进入日志；结束本轮或服务断开丢弃运行上下文。

WriteLedger 增加 HUMAN_HELD：尚未 Save 的已准备事项接管后进入此态，普通重跑只能查询。仅“新页面已核对 + 新确认 + 新票据”可恢复一次保存资格；WRITE_PENDING 接管后成为 UNKNOWN，始终只查。这样首次保存前用户删掉来源标记，也不会让普通重跑立即创建另一个事项。

沿用的标题/备注/新日期时间/提醒/截止作为 CanonicalItem.userDraft 持久化。原来源、原邮件提取快照和 key 保留，旧 choice/choiceDigest 清除；后续去重按修订核实，避免填回旧设置。仍需匹配当前授权账号、日历/列表和时区。SQLite 表结构不变，旧 JSON 默认无 userDraft；HUMAN_HELD 的旧 APK 降级不受支持。

只有离开后重开证据通过才记 VERIFIED。页面不明、确认后变化、保存回执丢失都保留检查点和未知状态；不会为了继续其他事项而离开未保存的人工编辑页。用户可再次接管处理，也可“结束本轮”，之后重新授权。

## 本地验证与设备边界

core 测试覆盖中断、检查点、新日期/提醒/截止、原生角色与备注两条路径、严格先后关系、跨日/夏令时、修订持久化/去重、冲突复查、剩余事项、Save 未知只查和 Broker 双排空屏障。

Android 测试使用生产 CalendarGuiPort、GuiNavigator、SessionBroker、本地存储及 CalendarConflictReader；模拟 shell、界面树、模型决定、动作回执和 Provider 游标。恢复新增事件提醒变动、通知/截止角色与备注路径的保存/重开、无效先后关系、确认后截止再变、人工已保存和重跑旧截止拒绝。未运行真实系统 CalendarProvider；窗口按钮仍只记录回调，未连通真实 WorkbenchController→Shizuku→App。

真机继续跳过。真实 Gmail/Calendar 字段、保存回执、加载/弹窗、主屏焦点和键盘、进程回收恢复均未验收。最终计数、构建与签名见 [本地检查](../evaluation/LOCAL_CHECKS.md)。
